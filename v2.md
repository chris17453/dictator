# Dictator v2 — Gap Analysis & Enterprise Rebuild Plan

**Subject:** the-dictator v1.0.2 · **Branch:** REFACTORING · **Commit:** `777ce22`
**Codebase:** 7,540 LOC across 16 modules in `src/`
**Assessed platform:** Fedora 42 · GNOME Shell 48.8 · Wayland · RTX 4090
**Date:** 2026-08-20

---

## Verdict — Rebuild, do not remediate

The product concept is sound. The implementation cannot reach the stated requirements by
incremental repair, for one decisive reason: **the entire input and output path is built on
`pynput`, an X11 technology, running on a Wayland session where it structurally cannot work.**
Global hotkeys cannot be grabbed and text cannot be injected into other applications. No amount
of keybinding configuration fixes this.

Everything else follows from a second decision — that a Qt window *is* the application. A
3,170-line `QMainWindow` owns the config, the state machine, the clipboard, the history, and the
transcription callbacks. Removing the UI, as required, means removing the application.

The correct target is a **headless user service** that holds the model warm, binds shortcuts
through whichever mechanism the session actually owns, and streams text into the focused field.
X11 and Wayland are both first-class, reached through one narrow backend interface with one
implementation each — not by branching at call sites, which is how the current code arrived here.
The UI becomes an optional, disposable client. Verified on this machine: every platform interface
required for both paths is already present.

## 2. Root Cause: no display-server abstraction

The session is Wayland (`XDG_SESSION_TYPE=wayland`, GNOME Shell 48.8). The keyboard layer is
`pynput`, whose Linux backend is an X11 client.

On Wayland, an X11 client is confined to XWayland. It cannot observe key events routed to native
Wayland surfaces, and `XTEST` injection reaches only the XWayland server — never the compositor's
real input path. The consequences are exact:

- **Hotkeys fire intermittently or never**, depending entirely on which application happens to
  hold focus — `src/hotkey_manager.py:87`.
- **Injected text goes nowhere.** `keyboard.type(text)` at `src/dictator.py:2115` silently
  succeeds and delivers nothing to a native Wayland application.
- **The failure is silent by design.** The permission self-test at `hotkey_manager.py:184` waits
  100 ms for any key event and, finding none, prints setup advice about the `input` group. That
  advice is a dead end here: this account is not in `input`, and joining it would not help,
  because the problem is not permissions.

### The precise defect

It is *not* that the code uses X11. X11 is a supported target and its interfaces work correctly on
an X11 session. The defect is that **there is exactly one code path, it is never guarded by a
session check, and it is the wrong one here.** There is no display-server abstraction to select
against.

That check is also less trivial than it looks, and this host demonstrates why:

```
$ echo "DISPLAY=$DISPLAY WAYLAND_DISPLAY=$WAYLAND_DISPLAY"
DISPLAY=:0 WAYLAND_DISPLAY=wayland-0        # both set, simultaneously
```

Under XWayland, `DISPLAY` is set on a Wayland session. Any detection written as *"if `DISPLAY` is
set, use X11"* — the obvious implementation — selects the broken backend on every modern desktop.
Detection must key on `XDG_SESSION_TYPE` first and treat `DISPLAY` as evidence only when no
Wayland display is present. Specified in §5.

### Verified on this host

The interfaces required to solve this on both display servers are present:

- **Wayland** — `org.freedesktop.portal.GlobalShortcuts` (v1) exposes both `Activated` *and*
  `Deactivated`: press and release, precisely what hold-to-talk needs.
  `org.freedesktop.portal.RemoteDesktop` (v2) exposes `NotifyKeyboardKeysym` and `ConnectToEIS`
  for real injection. `org.freedesktop.portal.Clipboard` is available.
- **X11** — `python-xlib 0.33` with a working `XTEST` extension is already installed, so a proper
  in-process X11 backend needs no new dependency and no shelling out to `xdotool`.

Neither path requires root, `input` group membership, or `/dev/uinput`.

```
CURRENT — X11 path, severed by Wayland
  keyboard ──▶ mutter ──✕──▶ XWayland ──✕──▶ pynput
                                              └─▶ XTEST inject ──✕──▶ focused app

TARGET — display-server-owned grab
  keyboard ──▶ mutter ──▶ GlobalShortcuts ──▶ dictatord
                                                  └─▶ RemoteDesktop ──▶ focused app
  keyboard ──▶ X server ──▶ XGrabKey ──────▶ dictatord
                                                  └─▶ XTEST ──────────▶ focused app
```

## 4. Target Architecture

One long-lived user service owns everything that must be warm, stateful, or privileged. Every
other component is a thin, replaceable client of its API. The UI becomes one such client —
optional, and never on the critical path.

```
PLATFORM ADAPTERS   GlobalShortcuts │ RemoteDesktop │ Clipboard │ XGrabKey │ XTEST │ PipeWire
                            ▲               ▲                        ▲         ▲        ▲
┌───────────────────────────┴───────────────┴────────────────────────┴─────────┴────────┴──────┐
│ DICTATORD — systemd user service, no display dependency                                       │
│                                                                                               │
│   Session FSM  ──▶  Ring buffer + VAD  ──▶  Streaming ASR  ──▶  Delivery                       │
│   idle/arming/     300 ms pre-roll         CUDA, resident      clipboard + paste               │
│   live/flushing                                                                               │
│                                                                                               │
│   Memory store        Lexicon              Config              Telemetry                      │
│   SQLite/FTS5/WAL     vocab + corrections  layered, validated  local, structured              │
└───────────────────────────────────────┬───────────────────────────────────────────────────────┘
                                        │
CONTROL PLANE   D-Bus com.watkinslabs.Dictator1 (session bus)
   Toggle · PushBegin/End · Cancel · SetDevice · Search · GetState
        ⟶ StateChanged · Partial · Final · Level · Delivered · Fault
                                        │
CLIENTS (optional, disposable)   dictator CLI │ Tray indicator │ Live overlay · TUI │ doctor
```

### 4.1 Why a daemon, specifically

Three requirements each independently force it. The model must be **resident**, because loading
weights on first keystroke costs seconds. The portal sessions must be **long-lived**, because
`RemoteDesktop` consent is granted per session and re-prompting on every utterance is unusable.
The audio device must stay **open**, because the first 300 ms of speech happens before a user's
finger leaves the key. A process that starts when you press a key can satisfy none of these.

### 4.2 Input: shortcuts owned by the display server

Shortcuts are bound once at first run, through whichever backend the session calls for — the
portal on Wayland, `XGrabKey` on X11 (§5). In both cases the display server itself owns the grab,
which is why the chord works regardless of which application has focus: the requirement to
*survive focus change* is satisfied structurally rather than defended against.

| Shortcut ID | Default binding | Press | Release |
|---|---|---|---|
| `toggle` | `Super`+`Space` | Start if idle; stop and deliver if live | Ignored |
| `push` | `Super`+`Shift` | Start; arm hold semantics | Stop and deliver |

Both behaviours come from one chord family and one code path — the release event is the only
difference. A press-and-release shorter than 250 ms on `push` promotes it to a toggle, so a user
who taps rather than holds is not punished with an empty transcript. That threshold is
configurable.

Because the two Tier 1 backends both deliver press *and* release, the state machine above them is
identical on X11 and Wayland. No requirement in this document is met on one display server and
merely approximated on the other; the sole exception is application-profile detection (§5.4).

### 4.3 Output: clipboard first, paste second, type last

Per-character keysym injection is slow, order-sensitive, and mangles anything outside the active
keyboard layout. The reliable primary path is: write the text to the clipboard, synthesise the
target application's paste chord, then restore the user's previous clipboard contents after a
short delay.

Both halves of R-6 are satisfied unconditionally — the clipboard *is* the delivery mechanism, so
text is always there, and the paste is what puts it in the field.

| Profile | Applies to | Chord | Rationale |
|---|---|---|---|
| `standard` | Default for GTK / Qt / Electron | `Ctrl`+`V` | Universal editable-field paste |
| `terminal` | VTE, Kitty, Alacritty, Foot | `Ctrl`+`Shift`+`V` | Ctrl+V is a control character |
| `vim-aware` | Terminals with a detected modal editor | type | Paste chords are unsafe in normal mode |
| `clipboard-only` | User-designated sensitive applications | — | Never synthesises input |

> **Profile selection is not symmetric across display servers.** Selecting a profile requires
> knowing which application has focus, and that is obtainable on X11 but **not on Wayland through
> any standard interface**. Verified here: `xdotool getactivewindow` aborts with
> `free(): invalid pointer` under XWayland, and `_NET_ACTIVE_WINDOW` returns only the XWayland
> stub window rather than the focused Wayland client. On X11 the profile is chosen automatically
> from `WM_CLASS`; on Wayland it must be chosen another way — see §5.4.

### 4.4 Streaming ASR and the live view

The pipeline inverts from record-then-decode to **capture-decode-emit**. A continuously-open
PipeWire stream feeds a ring buffer carrying 300 ms of pre-roll, so audio captured *before* the
chord registered is included — this alone eliminates the clipped-first-word problem. Silero VAD
segments speech; each closed segment is decoded on the resident CUDA model and emitted as a
`Final`. Between segments, a rolling window is decoded at roughly 400 ms cadence and emitted as a
`Partial`.

Partials are what make the live view possible, and the daemon emits them whether or not anything
is listening. The overlay, the TUI, and any future client are pure subscribers. **Delivery to the
focused field uses finals only** — partials are for display, never for injection.

### 4.5 The meter

The daemon emits a `Level` signal at 50 Hz carrying peak, RMS, a clip flag, and an 8-band
log-spaced magnitude vector computed from the same buffer the ASR consumes. That single signal
drives three renderings: a VU bar, a scrolling waveform, and a spectrum histogram. Clients choose;
no client computes DSP. The terminal client renders the same data as Unicode blocks, so a level
check needs no graphical session at all.

### 4.6 Memory

Two distinct things are meant by memory, and both are in scope.

**Transcript memory** — a SQLite database in WAL mode with an FTS5 index. Every utterance stored
with timestamp, duration, model, confidence, target application, and delivery outcome. This gives
`dictator search "quarterly forecast"`, replay of a mis-delivered transcript without re-speaking
it, and a retention policy that actually deletes. Audio retention is off by default and, when
enabled, is bounded by count and age.

**Adaptive memory** — the lexicon: the proper nouns, jargon, and identifiers you use that Whisper
does not know. Seeded explicitly, then grown from observed corrections; when a delivered
transcript is edited shortly afterwards in the same field, the edit is a supervision signal.
High-confidence terms are injected as the decoder's initial prompt; a deterministic post-ASR
substitution layer catches the rest. Both are inspectable and editable as plain text, because a
memory you cannot audit is a liability.

### 4.7 Ambient presence: the tray widget

"No UI" does not mean no presence. A dictation service that gives no feedback about whether it is
listening, which microphone it holds, or whether the last utterance was delivered is unusable for
a different reason than the current one. The resolution is an **ambient indicator** that occupies
no screen real estate and never takes focus — a tray item that is a status display, not a
launcher.

This is precisely where the current design goes wrong: its tray icon exists to summon the window
(`dictator.py:3118`). In the target, the tray item *is* the surface, a client of the same
`StateChanged` and `Level` signals as everything else.

| Element | Behaviour |
|---|---|
| Icon state | Idle, armed, live, transcribing, delivered, fault — distinguishable by **shape**, not only colour, so it reads for colour-blind users and in monochrome panels |
| Live meter | While a session is live, the icon animates as a compact VU indicator driven by `Level`, downsampled to panel cadence |
| Tooltip | Active device, model, session duration, last delivery target |
| Menu | Start/stop, device submenu with live presence marks, recent transcripts with copy and re-deliver, pause, open memory search, `doctor` summary, quit |
| Fault surfacing | A `Fault` signal marks the icon and puts the remedy one click away — the direct answer to G-08 |

The optional live-transcription overlay attaches to this item rather than being a separate window
to manage: shown while speaking, gone on delivery, never focusable, never in the tab order.

> **Verified on this host.** GNOME 48 does not implement the `StatusNotifierItem` tray protocol
> natively; it requires the AppIndicator shell extension, which **is installed and enabled here**
> (`gnome-shell-extension-appindicator-60`). Because that is an environmental dependency the
> product does not control, the tray item must be strictly optional and its absence detected and
> reported by `dictator doctor` — never assumed, never a prerequisite for dictation working.

### 4.8 Devices

Devices are addressed by stable PipeWire node name, never by the positional index that shifts
whenever a device is plugged in — the cause of G-14. The daemon subscribes to PipeWire's registry,
so appearance and disappearance are events, not errors discovered at the next start.

```
dictator devices              # list, with the active one marked
dictator devices set yeti     # fuzzy match on description
dictator devices cycle        # bindable to a third shortcut
dictator meter                # live levels in the terminal
```

Policy on disappearance is configurable: fail loudly, or fall back to the system default and say
so in a notification. The default is fallback with notification, because losing a sentence to a
Bluetooth headset dropping out is worse than a changed source.

## 5. Platform Support: X11 and Wayland

Both display servers are first-class targets. This is not achieved by branching at call sites —
that is how the current code arrived at G-00 — but by two narrow interfaces with one
implementation per platform, selected once at startup by capability probe and never consulted
again.

```
interface ShortcutBackend      bind(id, chord) · on_press · on_release · unbind
interface InjectionBackend     set_clipboard · restore_clipboard · send_chord
                               type_text · focused_app_id -> str | None
```

Everything above these interfaces — the session FSM, the ASR pipeline, memory, the tray, the CLI —
is display-server agnostic and has no import of either backend. Backends are the only place a
platform name appears.

### 5.1 Session detection

Probed in strict order, because the naive check is wrong on every XWayland-enabled desktop:

1. `XDG_SESSION_TYPE` — authoritative when set to `wayland` or `x11`.
2. `WAYLAND_DISPLAY` present and the socket connectable → Wayland.
3. `DISPLAY` present and the server connectable → X11.
4. Neither → headless. Shortcuts fall to `evdev`; injection is clipboard-only. `dictator toggle`
   over D-Bus still works, which is what makes the daemon testable in CI.

The resolved backend pair is reported in `GetState()` and by `doctor`, so a support conversation
begins with a fact rather than a guess.

### 5.2 Shortcut backends

| Backend | Session | Press | Release | Setup required | Notes |
|---|---|---|---|---|---|
| `portal` | Wayland — GNOME, KDE | Yes | Yes | One-time consent | Preferred. Compositor owns the grab. |
| `xgrabkey` | X11 — any WM | Yes | Yes | None | Preferred on X11. True grab, not a passive listener. |
| `evdev` | Both, plus TTY | Yes | Yes | `input` group | Universal fallback; works before a session exists. |
| `gsettings` | Wayland — GNOME only | Yes | **No** | None | Last resort. Toggle only — cannot do hold-to-talk. |

Both preferred backends deliver press *and* release, so hold-to-talk is native on X11 and Wayland
alike — one FSM, no per-platform behaviour difference. The `gsettings` path is the only degraded
mode, and because it cannot signal release, selecting it disables the `push` shortcut and says so
rather than binding a chord that silently records forever.

**X11 implementation notes.** `XGrabKey` is deceptively easy to get wrong, and these are the
defects that make hand-rolled X11 hotkeys feel flaky:

- A grab is registered against an *exact* modifier mask. The chord must be grabbed once for every
  permutation of the lock modifiers — `NumLock`, `CapsLock`, `ScrollLock` — or it stops responding
  the moment Num Lock is on. This is the single most common cause of "my hotkey works sometimes".
- Grab on the root window of every screen, not just the default.
- Handle `MappingNotify` and re-resolve keysyms to keycodes, or the chord breaks when the user
  switches keyboard layout.
- Handle `BadAccess` on grab as a real, reportable fault: another client already owns that chord.
  The user needs to be told which chord failed, not left with silence.
- Run the X connection on its own thread with its own display handle. Xlib is not thread-safe
  across a shared connection.

### 5.3 Injection backends

| Backend | Session | Clipboard | Paste chord | Direct type | Focused app |
|---|---|---|---|---|---|
| `portal` | Wayland — GNOME, KDE | Yes | Yes | Keysym | **No** |
| `xtest` | X11 — any WM | Yes | Yes | Yes | `WM_CLASS` |
| `uinput` | Wayland fallback | via `wl-copy` | Yes | Yes | **No** |
| `wtype` | wlroots — Sway, Hyprland | via `wl-copy` | Yes | Yes | **No** |

Clipboard ownership differs in a way worth planning for. On X11 a selection is held by a live
client, so the daemon must stay running to serve paste requests — it does, but a clipboard manager
should be recommended for users who expect text to survive a daemon restart. On Wayland the portal
and `wl-copy` handle ownership, with the same caveat.

### 5.4 The one real asymmetry, and how it is handled

X11 exposes the focused window's class; Wayland deliberately does not. Per-application paste
profiles are therefore fully automatic on X11 and require another mechanism on Wayland. Rather
than pretend otherwise, the design degrades explicitly, in this order:

1. **Configured default** — the `standard` profile, correct for the large majority of editable
   fields.
2. **Profile-bound shortcuts** — a second chord bound to `toggle-terminal` that delivers with the
   terminal profile. The user states intent through which key they press. This costs one
   keybinding and removes the guesswork entirely.
3. **Optional GNOME Shell extension** — a small extension exposing the focused window class on the
   session bus, restoring full parity. Ships separately, opt-in, never required.
4. **Learned override** — if a delivery is followed quickly by a manual correction, the daemon
   records the profile that was actually needed and offers it next time.

> **Security asymmetry, stated plainly.** X11 places no restriction on grabbing keys or injecting
> input — any client can do both to any other client, silently. Wayland's portal consent is not
> merely friction; it is the security property. The X11 backend is supported because users run
> X11, not because it is equivalent. `doctor` reports the active backend's trust model, and the
> documentation should be honest that an X11 session offers a keylogger-shaped surface that
> Wayland does not.

### 5.5 Supported configuration matrix

| Environment | Shortcuts | Injection | App profiles | Tier |
|---|---|---|---|---|
| GNOME · Wayland | `portal` | `portal` | Chord-bound or extension | **Tier 1** |
| Any WM · X11 | `xgrabkey` | `xtest` | Automatic | **Tier 1** |
| KDE Plasma · Wayland | `portal` | `portal` | Chord-bound | Tier 2 |
| Sway / Hyprland | `portal` or `evdev` | `wtype` | Chord-bound | Tier 2 |
| Headless / TTY / CI | `evdev` or D-Bus | Clipboard only | n/a | Tier 3 |

Tier 1 is covered by automated tests and blocks a release. Tier 2 is covered by a documented
manual smoke matrix run per release. Tier 3 is what CI actually exercises on every commit, which
is why the daemon is built to run without any display server at all.

### 5.6 How both backends get tested

The X11 backend is fully automatable: `Xvfb` plus a lightweight WM gives real grabs and real
`XTEST` injection in CI, and a test can assert that a synthesised chord produced a delivery into a
probe window. The Wayland portal path cannot be exercised that way, because the portal is a
user-consented service on a live session bus. It is covered instead by a **mock portal** — a test
double implementing `GlobalShortcuts` and `RemoteDesktop` on a private bus — which verifies the
daemon's contract with the portal, combined with the per-release manual matrix for the real thing.
Neither technique alone is sufficient; stating which one covers what is the difference between a
test suite and reassurance.

## 6. Service Contract

The D-Bus interface is the product's real API and the boundary every test targets. It is
versioned; the CLI and any UI are ordinary clients with no privileged access.

```
interface com.watkinslabs.Dictator1

methods
  Toggle(a{sv} options)            -> u session_id
  PushBegin(a{sv}) / PushEnd()     hold-to-talk, backend-driven
  Cancel()                         discard in flight, deliver nothing
  Redeliver(u id, a{sv})           re-inject a stored transcript
  SetDevice(s node_name)
  ListDevices()                    -> a(ssbb) name, desc, default, present
  Search(s query, u limit)         -> aa{sv} FTS5 over transcript memory
  GetState()                       -> a{sv} state, device, model, backends, uptime
  Reload()                         re-read config without dropping sessions

signals
  StateChanged(s state, a{sv} detail)
  Partial(u session_id, s text)          ~400 ms cadence, display only
  Final(u session_id, s text, d conf)
  Level(d peak, d rms, b clipping, ad bands)   50 Hz
  Delivered(u session_id, s method, s app_id, b ok)
  Fault(s code, s message, s remedy)     never a bare exception

properties
  State · Device · Model · Version · ShortcutBackend · InjectionBackend
```

Note `Fault`. Every failure carries a machine-readable code and a human remedy, replacing the 85
swallowed exceptions of G-19. A fault the daemon cannot phrase as a remedy is a defect in the
daemon, not a message for the user to decipher.

## 7. Non-Functional Requirements

Acceptance targets. Latency figures assume the RTX 4090 present on the assessed host, with
`large-v3-turbo` quantised to `int8_float16` and resident in VRAM.

| Attribute | Requirement | Target | Verified by |
|---|---|---:|---|
| Activation latency | Chord press → first sample captured | < 30 ms | Ring buffer pre-roll makes this negative in effect |
| Partial latency | Speech → partial on screen, p95 | < 500 ms | Streaming harness, fixed audio |
| Delivery latency | Chord release → text in field, p95 | < 700 ms | End-to-end timing suite |
| Accuracy | WER on the project's reference corpus | ≤ 6% | Nightly regression, fails the build on drift |
| Idle footprint | Resident set, model warm, no session | < 400 MB | Sampled by the daemon's own telemetry |
| Idle CPU | Steady state, device open | < 1% | Soak test, 24 h |
| Availability | Uninterrupted operation | 7 days | Soak test with device hot-plug injection |
| Recovery | Crash → serving again | < 5 s | `systemd` restart policy with backoff |
| Privacy | Audio and transcripts leaving the host | Never | Egress test asserts no network I/O post-model-fetch |
| Supply chain | Model weights verified before load | SHA-256 | Pinned manifest; load refuses on mismatch |

### 7.1 Security posture

- **TLS verification is restored unconditionally** (G-15). The certificate problem that motivated
  the bypass is a host trust-store issue and is diagnosed by `dictator doctor` with a real remedy.
  Disabling verification for the whole process is never the fix.
- **Model weights are pinned by digest** and verified before load (G-17). A mismatch is a hard
  failure.
- **The database is chmod 0600** under `$XDG_DATA_HOME`, with optional passphrase encryption at
  rest for regulated environments.
- **Redaction rules** — configurable patterns whose matches are delivered but never stored, so
  credentials spoken aloud do not persist in searchable memory.
- **The daemon runs unprivileged.** No `input` group, no `uinput`, no setuid on the Tier 1 paths.
  Every Wayland capability is portal-mediated and revocable by the user through the desktop's own
  settings.

### 7.2 Operability

`dictator doctor` is the single most valuable piece of this rebuild for support cost, and it
exists specifically because of G-08 — the current system's most damaging property is that it fails
silently and then misdiagnoses itself.

```
$ dictator doctor

  ✓ shortcut backend ..........  portal — v1, 2 shortcuts bound
  ✓ injection backend .........  portal — RemoteDesktop v2, session restored from token
  ✓ audio device ..............  Blue Yeti  (48 kHz, 1 ch)
  ✓ model .....................  large-v3-turbo  cuda:0, digest ok
  ✓ tls trust store ...........  verification enabled
```

## 8. Delivery Plan

Six phases. The ordering is deliberate: the riskiest unknown — whether portal input actually works
end to end — is resolved in Phase 0, before any code is committed to the new architecture. Each
phase ends at a demonstrable state.

### Phase 0 — Spike: prove both input paths

Two throwaway scripts, no product code.

- **Wayland:** bind a shortcut, capture `Activated` and `Deactivated`, open a `RemoteDesktop`
  session with `persist_mode`, set the clipboard and synthesise a paste into a native Wayland
  application.
- **X11:** the same round trip via `XGrabKey` and `XTEST` on an X11 session, including the
  lock-modifier permutations, with Num Lock and Caps Lock deliberately on.

**Exit criterion:** on each display server, a chord pressed in another application puts a known
string into its focused text field, and the Wayland case survives a reboot without re-prompting
for consent. If `persist_mode` does not persist, the fallback ladder in §5.2 is promoted before
Phase 1 begins. Testing X11 requires an X11 session — provision one now rather than discovering in
Phase 1 that nobody has logged into one.

### Phase 1 — Core: headless daemon, end to end

- New package alongside the old: `dictatord/` with platform, audio, ASR, delivery and control
  modules. No Qt import anywhere in it.
- **Platform layer per §5:** the two backend interfaces, session detection in the documented
  order, and all four Tier 1 implementations — `portal` and `xgrabkey` for shortcuts, `portal` and
  `xtest` for injection. Backend selection is logged and exposed through `GetState()` (G-00).
- Session FSM, PipeWire capture with 300 ms pre-roll ring buffer, Silero VAD.
- Resident CUDA model; honour configured model and device, deleting the hardcoded `tiny`/`cpu`
  path (G-12).
- D-Bus service per §6, systemd user unit with restart backoff.
- Delivery: clipboard set, paste synthesis, clipboard restore, per-app profiles (G-02, G-05,
  G-06).
- Restore TLS verification and pin model digests (G-15, G-17); turn the red security tests green.

**Exit criterion:** both chords work headless, in any application, surviving focus change, **on an
X11 session and a Wayland session**. R-1 through R-6 and R-12 met. The old UI still exists and is
untouched.

### Phase 2 — Streaming: partials, levels, live path

- Rolling-window decode emitting `Partial` at ~400 ms; segment-close emitting `Final` (G-11).
- `Level` signal at 50 Hz with peak, RMS, clip flag and 8-band magnitudes — replacing the
  stderr-scraping meter (G-10).
- Latency harness measuring the §7 percentiles on fixed audio; results recorded per build.

**Exit criterion:** R-9 and R-10 met at the API level, demonstrated by the terminal client. No
graphical UI required to prove it.

### Phase 3 — Memory: durable transcripts, devices, lexicon

- SQLite WAL store with FTS5; schema migrations from version one, because the first migration is
  always the one nobody planned for.
- `search`, `redeliver`, `prune`, `export`; retention policy and redaction rules (G-20).
- PipeWire registry subscription: devices by stable node name, hot-plug as an event, configurable
  fallback (G-14).
- Lexicon with correction learning and the deterministic substitution layer.

**Exit criterion:** R-7 and R-8 met. Microphone unplugged mid-utterance produces a clean
notification and a recovered session, not a stack trace.

### Phase 4 — Clients: optional surfaces

- **Tray indicator** — the primary ambient surface per §4.7. State by icon shape, live VU
  animation, device submenu, recent transcripts with re-deliver, fault remedies. Degrades cleanly
  to notifications where no tray host exists.
- **Live overlay** — a small, focus-refusing, click-through panel anchored to the tray item,
  showing partials as they arrive plus the VU bar, waveform and spectrum. Shown only while a
  session is live, and only if enabled.
- **TUI** — `dictator meter` and `dictator watch` for headless and remote diagnosis.
- **Configuration** — a file with a documented schema and `dictator config` to read and set it.
  The 2,308-line settings dialog is not rebuilt.

**Exit criterion:** every client can be deleted from the install without affecting dictation.

### Phase 5 — Harden: remove the old system, make it supportable

- Delete `dictator.py`, `settings_ui.py`, `color_picker.py`, `gui.py`, `common_ui.py`,
  `ui_utils.py`, `hotkey_manager.py`, `desktop_integration.py`, the root-level test scripts,
  `junk/`, `ai-temp/`, and the committed history JSON.
- Retire the 24 UI-coupled test modules; land the service-contract suite, the WER regression, and
  fault injection for device loss, portal revocation, model-load failure and disk-full.
- Platform coverage per §5.6: X11 backend under `Xvfb` in CI, Wayland backend against a mock
  portal on a private bus, and the Tier 2 manual smoke matrix documented as a release gate.
- `dictator doctor`, structured JSON logging, local metrics, config migration.
- Packaging: systemd user unit, RPM and Flatpak, one-command install that ends in a working chord.
- 24-hour soak with hot-plug injection; documentation rewritten around the daemon.

## 9. Risks & Open Decisions

| ID | Risk | Sev | Mitigation |
|---|---|---|---|
| K-1 | `RemoteDesktop` consent may not persist across reboots on GNOME 48 despite `persist_mode`. If it does not, every restart prompts. | 1 | Resolved in Phase 0 before commitment. Fallback ladder specified and probed at startup. |
| K-2 | Clipboard-paste delivery is visible to the target application and briefly perturbs clipboard state. | 2 | Save and restore with configurable delay; `clipboard-only` profile where synthesis is unwelcome. |
| K-3 | Streaming partials on a rolling window can revise text the user already read, which reads as flicker. | 2 | Emit partials with a stability prefix; render only the stable span as settled, the tail as provisional. Partials never drive delivery. |
| K-4 | Portal availability varies across compositors; KDE, Sway and older GNOME differ. | 2 | Capability probe at startup, adapters behind one interface, `doctor` reports which path is active. |
| K-5 | Resident CUDA model holds VRAM continuously on a shared workstation. | 3 | Configurable idle unload after *n* minutes. Default: stay resident. |
| K-6 | Correction learning could poison the lexicon from unrelated edits. | 3 | Require repeated observation before promotion; every entry inspectable and reversible; learning is opt-in. |
| K-7 | Supporting two display servers doubles the surface where behaviour can diverge, and divergence is discovered by users rather than tests. | 2 | Backend interfaces are deliberately narrow — five methods, one allowed to return null. Every contract test runs against both backends and a null backend. Divergence beyond §5.4 is a defect, not a platform difference. |
| K-8 | The X11 backend has no consent model: it can grab and inject silently, and inherits X11's absent isolation between clients. | 3 | Documented plainly rather than papered over; `doctor` reports the active trust model. Wayland remains the recommended session. |
| K-9 | On X11 the clipboard selection is owned by a live client, so text vanishes if the daemon exits before the user pastes. | 3 | Detect absence of a clipboard manager at startup and say so once; hold the selection until delivery is confirmed. |

### Decision recorded — platform scope

**X11 and Wayland are both Tier 1** and both gate a release, per §5.5. KDE Plasma and wlroots
compositors remain Tier 2 — they work through the same backends and are covered by the manual
smoke matrix, but they do not block a release. The practical cost is one extra backend pair in
Phase 1 and an X11 session provisioned for Phase 0; the architecture was already shaped to absorb
it, because the alternative — branching at call sites — is the defect this rebuild exists to
remove.

### Decisions required before Phase 1

1. **Default chords.** `Super`+`Space` collides with the input-method switcher on some
   configurations. Alternatives: a double-tap of a modifier, or `Super`+`Alt`. The backends let
   the user rebind, but the default should not collide out of the box.
2. **Model tier.** `large-v3-turbo` at `int8_float16` is the recommended default for this
   hardware. If the product must also run acceptably on CPU-only machines, the tier must be
   selected by capability probe rather than assumed.
3. **Audio retention default.** Recommendation is off. Retaining audio makes accuracy debugging
   far easier and makes the memory store far more sensitive.
4. **Wayland-only profile parity.** Whether to ship the optional GNOME Shell extension of §5.4 for
   automatic application detection, or to rely on profile-bound shortcuts alone. The extension
   buys parity with X11 at the cost of a second packaged component and a second thing to break on
   GNOME upgrades.
